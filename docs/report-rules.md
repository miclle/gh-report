# 报告业务规则

## 报告类型

工具支持四种报告类型，通过子命令区分：

| 子命令 | 类型 | 默认拉取天数 | 时间过滤基准 |
|--------|------|-------------|-------------|
| （无）/ `daily` | 日报 | 1 天 | 当天零点 |
| `weekly` | 周报 | 14 天（两周） | 本周一零点 |
| `monthly` | 月报 | 60 天（两个月） | 本月一号零点 |
| `yearly` | 年报 | 730 天（两年） | 今年一月一号零点 |

不指定子命令时默认为日报。用户可通过 `-d` 参数覆盖默认拉取天数。

## 工作条目

"工作条目"展示用户在**报告时间范围**内参与的工作活动。时间范围的起点由报告类型决定（见上表"时间过滤基准"列），终点为当前时间。

### Pull Request

| 状态 | 是否纳入 | 说明 |
|------|----------|------|
| open / draft | 是 | 进行中的工作，始终展示 |
| 时间范围内合并 | 是 | 该周期完成的工作 |
| 时间范围内关闭 | 是 | 该周期关闭的工作 |
| 时间范围之前已合并或已关闭 | 否 | 不属于该周期的工作 |

- 仅展示用户作为作者的 PR
- 有 Assignees 但不包含当前用户的 PR 不展示

### Issue

| 状态 | 是否纳入 | 说明 |
|------|----------|------|
| open | 是 | 进行中的工作，始终展示 |
| 时间范围内创建 | 是 | 该周期新建的工作 |
| 时间范围内关闭 | 是 | 该周期完成的工作 |
| 时间范围之前已关闭 | 否 | 不属于该周期的工作 |

- 仅展示用户创建的 Issue
- 有 Assignees 但不包含当前用户的 Issue 不展示

### 评论

- 仅展示**时间范围内**发表的评论
- 用户在**自己 PR/Issue** 上的评论不单独列出（已作为 PR/Issue 条目体现）
- 仅展示在**他人 PR/Issue** 上的评论，视为参与讨论或 Code Review
- 同一个 Issue 或 PR 的多条评论合并为一条记录

### Review

- 仅展示**时间范围内**发表的 Review 评论
- 用户在**自己 PR** 上的 Review 不单独列出
- 仅展示对**他人 PR** 的 Review，视为 Code Review 活动
- 同一个 PR 的多条 Review 合并为一条记录

## 计划条目

"计划条目"展示用户接下来需要推进的工作，不按日期过滤。根据报告类型，标题分别为"明日计划"、"下周计划"、"下月计划"、"下年计划"。

### 来源 1：未完成的 PR

- 用户作为作者的 open 或 draft 状态 PR
- 已合并或已关闭的 PR 不纳入
- 有 Assignees 但不包含当前用户的 PR 不纳入

### 来源 2：当前迭代项目

- 属于**当前迭代**的项目 Item（迭代周期包含今天）
- Assignees 包含当前用户
- 状态不是 Done、Closed 或 Merged
- 如果某条 Item 已作为未完成 PR 出现，则合并展示并补充项目状态信息

### 去重

两个来源先按 `仓库#编号` 去重，再按照下述任务归并规则合并关联的 Issue 和 PR。

## 任务归并与链接

Summary 和 AI 模式以任务为展示单位；CSV 保留原始分类明细。

- 仅使用 GitHub `closingIssuesReferences` 返回的明确关联（含手动关联）。标题相似、普通提及、依赖关系不作为归并依据。
- 一个 Issue 对应一个或多个 PR：以 Issue 标题描述任务，保留 Issue 和每个纳入报告的 PR 的完整 URL。多个 PR 分别展示进展及实现标题。
- 一个 PR 对应多个独立 Issue：各 Issue 仍为独立任务，可以引用同一个 PR，不沿共享 PR 合并任务。
- 直接展示完整 URL，不使用 Markdown 链接或尖括号包装；URL 自身包含仓库、类型路径和编号，支持跨仓库关联并避免同号混淆；评论和 Review 保留原始锚点链接。
- 先按原有时间、用户和计划规则筛选活动，再归并。关联 Issue 不符合本期活动条件时，只作为任务背景，明确标注“不计本期活动”，不补造该用户的创建、关闭或完成记录。也不自动补入未通过筛选的 PR。
- 本期工作与后续计划分别归并，同一任务可以出现在两个部分；计划部分只展示描述和链接。
- Issue 和各 PR 分别保留状态；PR 合并不代表任务已完成、发布或验收，PR 关闭不等于合并。非日报保留每个活动来源的日期，背景 Issue 不补造日期。
- 未关联的记录独立展示。关联查询失败时向 stderr 提示，并保留该 PR 的独立条目，不使用部分分页结果归并。

例如：

```text
- 支持 PostgreSQL 存储 | https://github.com/team/tasks/issues/100 进行中 | https://github.com/team/code/pull/120 已合并
```

覆盖边界：必须在 GitHub 上存在明确关系。关闭关键词只有在 GitHub 支持的条件下才会建立关系（例如 PR 目标分支为默认分支）；普通正文引用或提交消息中的引用不保证出现在该接口结果中。程序不会用文字猜测补齐这些关系。

## 数据获取范围

`days` 参数控制从 GitHub 拉取多远的数据。每种报告类型有不同的默认值（日报 1 天、周报 14 天、月报 60 天、年报 730 天），用户可通过 `-d` 覆盖。该参数影响数据获取量，但不影响工作条目的展示范围——工作条目始终只展示报告时间范围内的活动。`days` 较大时，可以为计划条目提供更完整的项目迭代上下文。

## 用户过滤

指定 `--user` 时，报告仅包含该用户相关的活动：

| 数据类型 | 过滤条件 |
|----------|----------|
| PR | 用户是作者 |
| Issue | 用户是创建者，且 Assignees 包含用户（或无 Assignees） |
| 评论 | 用户是评论者 |
| Review | 用户是 Review 者 |
| 计划条目（项目） | Assignees 包含用户 |

未指定 `--user` 时，展示所有用户的活动。

## 状态展示映射

### PR 状态

| 原始状态 | 展示文本 |
|----------|----------|
| merged | 已合并 |
| open + 有 Review | 已提交(审查中) |
| open + 无 Review | 已提交 |
| draft | 草稿 |
| closed | 已关闭 |

### Issue 状态

| 原始状态 | 展示文本 |
|----------|----------|
| open | 进行中 |
| closed | 已关闭 |

## 计划条目格式

- 不包含任何状态或优先级标识（如 Testing、开发中、Todo、P0、P1 等）
- 仅展示任务标题和全部来源的完整 URL（直接展示，不使用 Markdown 链接包装）
